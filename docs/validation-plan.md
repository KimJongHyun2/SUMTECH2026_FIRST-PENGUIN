# 검증 계획과 미해결 조건

팀 제공 인터뷰 E1~E3·five_whys·why_ours를 문제 정의의 근거로 사용한다. 문서 형식·정책 일치·가상 산술과 실제 앱·기기·E2E·효과를 각각 검증한다.

## 1. 스타터킷 대조 범위

대조한 키트의 파일과 규칙은 [Starter Kit 제출 규칙 대조](starter-kit-review.md)를 따른다.

문제정의는 예시의 statement·canvas·personas·experiences·sources·five_whys·solution_paths·insight·features 구조를 따른다. 흐름은 platform·platformReason·scenarios 구조, 3~8개, S+숫자 고유 ID, 제목 1~120자, 단계 1~12개, 기대 결과 1~500자를 확인한다. 로그인 없는 서비스이므로 account를 생략한다.

형식 검사는 문서 파싱·키·개수·문자 수를 확인한다. 독립성·UI 이동·근거의 적합성과 상태 전이는 문서 간 수동 대조를 병행한다. 전부 자동 검사됐다고 표현하지 않는다.

## 2. 독립 실행 조건

각 흐름은 기록·기준·설정이 없는 별도 브라우저 context에서 첫 화면(/)부터 시작한다. context는 저장 공간을 격리하는 실행 환경이며 다른 흐름의 storageState·세션 ID·QR·계정을 주입하지 않는다. 필요한 기준·세션·리포트·QR은 해당 흐름 안에서 생성한다. 실제 이용자의 기존 기록을 지우는 절차가 아니다. 서버의 빈 DB만으로 브라우저 로컬 저장 초기화가 보장되는 것은 아니므로 둘을 구분한다.

기본 경고 10초·재경고 60초를 사용한다. UI 버튼 뒤에는 실제 처리 완료를 기다린다. 기준 등록 클릭 뒤 안정 5초 대기는 별도 기능을 생략한 것이 아니다. 권한 사전 허용이 없는 환경은 '카메라 켜기' 직후 브라우저 권한창의 '허용'을 처리한다. UI 이동은 첫 화면 이후 버튼·메뉴로 하며 주소·API로 건너뛰지 않는다.

운영·실기기 시험의 카메라·정면/측면 배치·자세 유지·자리 비움·QR 스캔·네트워크 끊김은 실제 입력 조건이다. E2E에는 PRD §5.1·§8.1의 명시적 예외를 적용한다. `NODE_ENV=test` 및 테스트 도구 활성화 조건에서 결정적 정면 입력을 공급하고, S3의 첫 자동 주기를 유효 3초로 대체하며 S5·S6의 QR 스캔·휴대폰 입력·장애를 테스트 버튼으로 주입한다. 승인·등록·판정·집계·저장은 공통 경로로 수행하고 최종 결과를 직접 생성하지 않는다.

## 5. 테스트 실행 정책과 남은 구현 조건

S3은 테스트 전용 시계·주기 주입으로 첫 자동 주기를 유효 3초로 가속하도록 설계한다. 첫 생성 후 다음 주기를 1800초로 복원하고 등록·경고·복귀·재경고는 가속하지 않는다. V=3초인 테스트 리포트를 V=1800초로 표시하지 않으며 테스트 표시를 남긴다. 운영 1800초 경계·보류 시간 제외·경계 종료 중복 방지는 별도로 검증한다. 종료 부분 리포트로 자동 리포트를 대체하지 않는다.

S5·S6은 단일 PC의 '테스트 도구'→'[테스트용] 측면 데이터 주입'으로 QR 스캔·휴대폰 요청을 생략하며 PC 승인·기준 등록·딥 시작은 실제 UI로 수행한다. 이탈·복귀 재생 버튼은 양쪽 이탈 10초·복귀 3초를 연속 공급해 클릭 지연이 D=13초를 늘리지 않게 한다. 연결 끊기 버튼은 측면 입력 중단·연결 끊김·종료 무응답을 주입한다. 복구 대기 후 '기본 모드로 계속'을 눌러 동일 세션의 새 모드 구간과 종료를 확인한다. 운영의 실제 QR·다중 기기·HTTPS·동기화·휴대폰 자체 종료 시험은 별도로 남긴다.

Docker·E2E·배포의 스타터 요건도 기획 점수표와 구분한다. 기본 브랜치 파일, app 포트 3000, /__health와 실제 releaseId, 흐름별 spec/test 하나, 빈 DB 독립 입력을 후속 구현에서 검증한다. 키트의 mock/skip 제한과 테스트 시계·입력 주입 허용 범위는 제출 전에 확인한다. 테스트 도구·S1~S8 spec·실행 시간은 후속 구현 검증 대상이다.

## 6. 점수·효과 검증

현재 점수는 사용자 전달 기준 14.6/30이며 목표는 20점대 상위권이다. 목표 달성은 대시보드 재평가로 확인한다. 자가 검사 결과는 문서 구조 검증이다.

문제 검증은 실제 대안 사용·반복 빈도·불편·사용 의향을 확인한다. 감지 검증은 사람·세션 분리, 독립 참조, 정밀도·놓침·시간당 오경고를 기록한다. 가치 검증은 같은 작업의 무알림/시간 기반/변화 기반 조건에서 조정·무시·작업 방해·재사용 의향을 기록한다. 합격 허용치는 실험 전에 팀이 정한다.

## 7. P0/P1의 출처와 기획 우선순위

새 스타터킷에는 공식 P0/P1 등급표·30점 세부 배점표가 없다. problem.example.yaml의 P1은 페르소나 ID이며 우선순위 등급이 아니다. 아래 분류는 스타터의 필수 요건과 실제 위험을 묶은 팀 내부 작업 우선순위이다. 주최측 공식 배점이나 점수 상승 예측으로 사용하지 않는다.

| 내부 우선순위 | 스타터에서 확인한 기준/위험 | 현재 처리·한계 |
|---|---|---|
| P0 | 제출 경로·YAML 필수 키·3~8개 흐름·단계/문자 수 규격이다. | 최종 문서를 대조·검사한다. |
| P0 | 앞 흐름 데이터에 의존하지 않고 chosen 경로를 끝까지 수행해야 한다. | 각 흐름이 첫 화면에서 자체 기준·기록·연결을 생성한다. 실제 UI 실행은 미검증이다. |
| P0 | 기존 키트는 흐름 생략·가짜 응답/상태를 제한한다. | 최신 사용자 지시의 테스트 예외는 입력/리포트 주기만 대체하고 공통 판정·저장을 실행하도록 설계한다. 주최측 수용 여부와 실제 실행은 별도 확인한다. |
| P1 | 실제 장면·원인·영향·대안과 why_ours·관찰 가능한 기능 완료 조건을 연결한다. | E1~E3의 원문과 외부 출처의 적용 범위를 보존한다. |
| P1 | 용어·수치·중단·저장·삭제·집계 규칙이 일치해야 한다. | 공통 정책을 단일 기준으로 삼고 최종 YAML·PRD·집계 계약을 대조한다. |

보관 기간, QR 만료 시간, 연결 감시/장애/자체 중단 시간과 사용자 설정 허용 상한은 구현·실기기 시험을 통해 확정한다. 이전 제안값은 archive/planning-history/planning-policy.before-cleanup.yaml에 보존하며 현재 완료 조건에 적용하지 않는다. 관련 기능과 실패 처리는 유지한다.

## 8. 인지와 이탈 비율의 검증 설계

문제는 ‘작업 몰입 중 자세 인지 불능(Unawareness)’, 목표는 ‘지속 이탈에 대한 즉각적 피드백으로 인지까지 걸리는 시간 단축’, 주 지표는 `R=D/V×100(%)`이다. 경고·사용자 인지·복귀는 서로 다른 사건이다. 시간·집계 정의는 [PRD](prd.md), [공통 정책](planning-policy.yaml), [집계 계약](report-contract.md#4-성공-지표-계약--자세-이탈-비율)을 따른다.

### 단계별 검증과 수집 항목

| 검증 | 방법 | 관찰·기록 | 실패·판단 유보 조건 |
|---|---|---|---|
| 문제 | E1~E3의 장면을 바탕으로 실제 노트북 작업을 관찰한다. | 반복 빈도·인지 계기·현재 대안·사용 의향이다. | 자세 미인지와 환경·유지 불편의 영향을 구분해 기록한다. |
| 감지 | 사람·촬영 세션을 분리하고 독립 참조와 판정 결과를 비교한다. | 정밀도·놓침·시간당 오경고·유효 시간·보류 사유이다. | 감지 경계를 평가 자료에 맞추거나 보류 증가로 R만 낮추면 가치 입증에 쓰지 않는다. |
| 인지 | 동의받은 별도 관찰 실험에서 사용자에게 알아차린 시점을 보고받는다. | 이탈 시작·알림 표시·인지 보고·복귀 확인 시각을 각각 기록한다. | 인지 보고가 없으면 해당 관측값을 비워 두고 분석에서 구분한다. 복귀·알림을 인지의 대리 시각으로 채우지 않는다. |
| 가치 | 같은 사용자의 같은 작업에서 무알림·고정 시간·변화 기반 조건을 비교한다. | 각 조건 V·D·R, 인지 지연, 작업 중단·무시·재사용 의향이다. | 비교 조건 차이·자료 부족·작업 방해 증가를 함께 보고한다. R 감소만으로 예방 효과를 주장하지 않는다. |

작업 순서·난이도·촬영 조건 차이를 기록하고 가능한 동일 조건에서 비교한다. 시간 기반 알림의 주기, 참가자 수, 최소 유효 관찰 시간, 목표 감소폭, 오경고·작업 중단 허용치를 실험 전에 팀이 확정한다. 실험 전에 정한 기준으로 결과를 판단한다. 조건별 R의 차이는 %p로 기록하고 반복 세션별 편차도 함께 본다. 제품에서 작업 난이도·인지 시점을 자동 수집한다고 약속하지 않는다.

인지 지연은 `인지 보고 시각 - 이탈 시작 시각`이다. 알림 전달 지연은 `실제 알림 표시 시각 - 10초 지속 조건 충족 시각`이며 서로 구분한다. 주관적 인지 보고의 오차도 기록한다. ‘즉각적’이라는 기획 목표를 0초 지연 성능 보장으로 해석하지 않는다.

### 문서 수용 기준과 실제 효과의 구분

- 문서 수용은 최신 스타터의 정확한 키·길이·단계·독립성, 운영 정책 시간 5/10/3/60/1800초와 S3 테스트 첫 주기 3초 예외, V=0 처리, 보류·전환·합산 산술이 일치하는 경우이다.
- S4는 이탈 6초와 복귀 후 4초를 합산하지 않는지, 첫 후보는 V에만 포함하고 보류는 V·D에서 제외하는지 확인한다.
- S6은 측면 입력 무효 시 즉시 보류·타이머 초기화, 연결 끊김 확인 후 복구 대기, 유효 정면 기준·입력과 사용자 선택 후 전환, 같은 세션의 별도 모드 구간을 확인한다. 정면 무효 시 전환 불가도 경계 수용 기준이다.
- 문서 검사·인지 향상·예방 효과·주최측 실행은 각각 별도의 근거로 확인한다.
- 최신 키트의 원본 식별·정확한 요구사항은 [starter-kit-review.md](starter-kit-review.md)에 기록한다. 공식 P0/P1 표는 없으며 내부 우선순위와 구분한다.
