# 검증 계획과 미해결 조건

2026-10-30 파일 격리·기획 정합성 정리본이다. 이번 범위는 실험 파일 격리, 그에 필요한 경로 정리, 기획 문서 수정과 문서 검사이다. posture-web/의 앱·카메라·기기·E2E·CI·배포는 실행하지 않는다. 문서 형식 통과와 실제 재현 성공을 구분한다.

## 1. 스타터킷 대조 범위

요청한 주최측 API에 POST해 응답의 downloadUrl로 새 ZIP을 받았고, 별도 임시 폴더에 풀어 START_HERE.md·problem.example.yaml·scenarios.example.yaml·관련 단계 안내·체크리스트를 확인했다. 팀 코드·서명 다운로드 주소는 제출 문서에 남기지 않는다.

문제정의는 예시의 statement·canvas·personas·experiences·sources·five_whys·solution_paths·insight·features 구조를 따른다. 흐름은 platform·platformReason·scenarios 구조, 3~8개, S+숫자 고유 ID, 제목 1~120자, 단계 1~12개, 기대 결과 1~500자를 확인한다. 로그인 없는 서비스이므로 account를 생략한다.

형식 검사는 문서 파싱·키·개수·문자 수를 확인한다. 독립성·UI 이동·근거의 적합성과 상태 전이는 문서 간 수동 대조를 병행한다. 전부 자동 검사됐다고 표현하지 않는다.

## 2. 독립 실행 조건

각 흐름은 기록·기준·설정이 없는 별도 브라우저 context에서 첫 화면(/)부터 시작한다. context는 저장 공간을 격리하는 실행 환경이며 다른 흐름의 storageState·세션 ID·QR·계정을 주입하지 않는다. 필요한 기준·세션·리포트·QR은 해당 흐름 안에서 생성한다. 실제 이용자의 기존 기록을 지우는 절차가 아니다. 서버의 빈 DB만으로 브라우저 로컬 저장 초기화가 보장되는 것은 아니므로 둘을 구분한다.

기본 경고 10초·재경고 60초를 사용한다. UI 버튼 뒤에는 실제 처리 완료를 기다린다. 기준 등록 클릭 뒤 안정 5초 대기는 별도 기능을 생략한 것이 아니다. 권한 사전 허용이 없는 환경은 '카메라 켜기' 직후 브라우저 권한창의 '허용'을 처리한다. UI 이동은 첫 화면 이후 버튼·메뉴로 하며 주소·API로 건너뛰지 않는다.

카메라·정면/측면 배치·자세 유지·자리 비움·QR 스캔·네트워크 끊김은 실제 입력 조건이다. 이 입력을 주최측이 제공하는 방법은 미확인이다. 향후 저장소의 동의받은 영상 자료를 실제 추론으로 처리하는 방안도 운영진 허용 확인과 자료 준비가 필요하다. 이번 작업에서 fixtures·E2E·제품용 시험 입력 UI를 구현하지 않았고, 가짜 상태·시간 조작으로 입력을 대체하지 않는다.

## 5. 해결되지 않은 실행 제약

S3은 실제 유효 1800초를 요구한다. 스타터킷 steps/03-delivery.md 3-4의 로컬 흐름 1분 이내 요구와 현재 양립하지 않는다. 자동 주기를 몰래 줄이거나 시계를 조작하거나 종료 부분 리포트로 대체하지 않는다. 주최측이 허용하는 짧은 재현 방식이 확인되어도 실제 기본 1800초 시험을 별도로 기록해야 한다. 현재는 형식 정리 완료·실행 규격 충돌 미해결이다.

S5·S6은 desktop이라는 platform 값만으로 휴대폰 동시 입력을 보장받지 못한다. 카메라 자동 입력·두 브라우저/기기·HTTPS·QR·동기화 지원을 확인해야 한다. 운영진 문의는 이번 작업에서 전송하지 않았다.

Docker·E2E·배포의 스타터 요건도 기획 점수표와 구분한다. 기존 안내의 기본 브랜치 파일, app 포트 3000, /__health와 실제 releaseId, 흐름별 spec/test 하나, 빈 DB 독립 입력, 금지된 mock/skip 없는 실제 실행 조건을 후속 구현에서 검증한다. 이번 문서 검사로 충족됐다고 표시하지 않는다.

## 6. 점수·효과 검증

현재 점수는 30점 만점에 14.6점이며 20점대 이상은 목표이다. 만점과 현재값은 사용자 확인값이고 목표 달성은 미확인이다. 세부 배점·실제 감점 이유·현재 문서의 재채점은 미확인이다. 자가 검사 결과를 점수로 바꾸지 않는다.

문제 검증은 실제 대안 사용·반복 빈도·불편·사용 의향을 확인한다. 감지 검증은 사람·세션 분리, 독립 참조, 정밀도·놓침·시간당 오경고를 기록한다. 가치 검증은 같은 작업의 무알림/시간 기반/변화 기반 조건에서 조정·무시·작업 방해·재사용 의향을 기록한다. 합격 허용치는 실험 전에 팀이 정한다.

## 7. P0/P1의 출처와 이번 기획 우선순위

새 스타터킷에는 공식 P0/P1 등급표·30점 세부 배점표가 없다. problem.example.yaml의 P1은 페르소나 ID이며 우선순위 등급이 아니다. 아래 분류는 스타터의 필수 요건과 실제 위험을 묶은 팀 내부 작업 우선순위이다. 주최측 공식 배점이나 점수 상승 예측으로 사용하지 않는다.

| 내부 우선순위 | 스타터에서 확인한 기준/위험 | 현재 처리·한계 |
|---|---|---|
| P0 | 제출 경로·YAML 필수 키·3~8개 흐름·단계/문자 수 규격이다. | 최종 문서를 대조·검사한다. |
| P0 | 앞 흐름 데이터에 의존하지 않고 chosen 경로를 끝까지 수행해야 한다. | 각 흐름이 첫 화면에서 자체 기준·기록·연결을 생성한다. 실제 UI 실행은 미검증이다. |
| P0 | 흐름을 건너뛰거나 가짜 응답·상태를 사용하면 안 된다. | 물리 입력·카메라·다중 기기 재현과 30분/1분 충돌은 미해결로 남긴다. |

보관 기간, QR 만료 시간, 연결 감시/장애/자체 중단 시간과 사용자 설정 허용 상한은 이전 문서의 제안값이다. 해당 숫자는 archive/planning-history/planning-policy.before-cleanup.yaml에 보존하고 현재 확정 완료 조건에서 제외한다. 관련 기능 자체와 실패 상태는 유지하며 수치 결정·실기기 시험은 미확정으로 남긴다.
