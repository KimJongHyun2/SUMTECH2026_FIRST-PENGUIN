## PRD 구조·내용에서 남는 문제

1. **서류가 없는 것이 아니라 결정이 흩어져 있다.** PRD 본문에는 발표 대본, 화면 명세, 알고리즘, 출처, 제출 운영이 섞여 있다. problem.yaml의 F1~F6와 PRD의 C/T/A/S/R 기능 ID 사이 연결표가 없고, PRD의 S1~S6 시나리오와 기능 명세의 S01 같은 표기도 혼동을 만든다. 저장소에는 참조한 원본 기능 명세서·개발 상세의 완전한 파일이 없다.
2. **정정 내용이 앞부분에 반영되지 않았다.** detection-basis.md 30·41행은 2026 논문과 10%를 근거처럼 쓰지만 89행은 그 논문을 찾지 못했고 10%는 근거 없는 설계값이라고 정정한다. 독자가 어느 쪽을 믿어야 하는지 판단해야 하는 구조다.
3. **상태 표가 낡았다.** PRD 241행과 progress에는 경험·출처가 학생 답 대기라고 남아 있지만 problem.yaml에는 이미 기재돼 있다. scoring-strategy의 “scenarios 아직 없음”도 현재와 다르다.
4. **화면 문구가 충돌한다.** F1 완료 조건은 “기준 자세가 저장됐어요”, S1과 PRD는 “기준 자세가 등록됐어요”다. 문구를 그대로 찾는 테스트를 계획했으므로 한 가지로 통일해야 한다.
5. **정밀해 보이는 숫자가 실제 결정 규칙을 대신한다.** 얼굴 +10%, 머리–어깨 −10%, 어깨 변위가 AND인지 OR인지, 어깨 이동을 어떻게 보정하는지 없다. 이탈 횟수의 “지속 조건”이 무엇인지도 불분명하다. 29초 이탈 뒤 복귀한 경우·복귀 중 다시 이탈한 경우의 집계를 예시로 명시할 필요가 있다.
6. **가치 실험이 차별성 주장과 맞지 않는다.** PRD 214행의 알림 끔/켬 비교는 알림의 유무를 비교한다. 자세 기반이 시간 기반보다 낫다는 주장을 하려면 시간 기반 비교 조건이 필요하다. 먼저 오탐·놓침을 별도 참조로 확인해야 자체 리포트 감소를 제대로 해석할 수 있다. 3명 실험은 탐색적 제품 점검이지 일반 사용자 효과의 증명이 아니다.
7. **핵심 위험의 실패 기준이 없다.** 임계값을 실험으로 정한다고 썼지만, 언제까지 어느 수준을 만족하지 못하면 범위나 주장을 줄일지 없다. “팬이 돌 정도로 높지 않다”는 성능 완료 조건도 기기마다 달라 재현하기 어렵다.

| 4개 화면·로컬 저장·기본 리포트 | 낮음~중간 | 상태·집계 정의가 명확해지면 비교적 정형적이다. |
| 웹캠에서 얼굴·어깨 특징 얻기 | 중간 | 모델 초기화·좌표계·인식 실패·기기 성능을 처리해야 한다. |
| 기준 변화와 의자 이동·필기 등을 구분 | 높음 | 랜드마크 추출과 유용한 판정은 별개다. 사용자·세션을 바꿔 확인해야 한다. |
| 다른 창에서 작업 중 계속 감지·알림 | 높음 | 이 서비스의 핵심 사용 장면이며 브라우저 수명주기와 성능 검증이 필요하다. |
| 주최 측 환경에서 재현 가능한 카메라 E2E | 높음 | 자체 실행 설정과 실제 영상 입력을 어떻게 연결할지 미정이다. |
| 딥 모드의 두 기기 연결·통합 | 매우 높음 | 현재 보류 유지가 합리적이다. |

브라우저 위험은 추측만은 아니다. [MDN requestAnimationFrame 문서](https://developer.mozilla.org/en-US/docs/Web/API/Window/requestAnimationFrame)는 대부분의 브라우저에서 백그라운드 탭의 호출이 정지한다고 설명한다. 따라서 이 방식으로 추론 루프를 만들 경우 탭 전환 후에도 계속 탐지된다고 가정할 수 없다. 모든 백그라운드 구현이 불가능하다는 뜻은 아니다.

[MediaPipe 공식 웹 문서](https://developers.google.com/edge/mediapipe/solutions/vision/pose_landmarker/web_js)는 추론 호출이 메인 스레드를 막을 수 있으며 Worker 사용을 안내한다. 알림 API를 붙이는 것과 안정적으로 감지·알림을 유지하는 것은 서로 다른 작업이다.

출처 차용에도 범위가 있다. [R1 원문](https://pmc.ncbi.nlm.nih.gov/articles/PMC12292650/)에서 안과 전공의 5명에게 웨어러블 진동 피드백을 30초 지연으로 준 것은 확인했다. 이것은 출발 설계의 참고이지 우리 정면 웹캠·학생 사용 장면에서 30초가 최적이라는 검증은 아니다. R8 원문 PDF는 이번 확인에서 타임아웃이 났으므로 기존 문서의 연구 요약을 새로 검증했다고 주장하지 않는다.

## 수정 우선순위

1. **사용자 문제를 좁히고 근거의 역할을 바로잡는다.** E1의 실제 장면을 중심으로 context/customer/impact/insight를 연결한다. 반복 빈도·손실·대안 사용 경험은 실제 확인한 만큼만 기록한다. 사회 전체 통계로 사용자 측정을 대신하지 않는다.
2. **대안 비교와 주장 수위를 고친다.** 완치 기준을 제거하고 자세 인지·작업 방해·사용 부담 등 동일한 목표로 비교한다. 시간 기반보다 낫다는 것은 검증할 가설로 둔다. 유사한 자세 피드백 접근과의 차이를 실제 조사·경험 범위에서 설명한다.
3. **카메라 입력 재현과 백그라운드 동작을 먼저 검증한다.** 실패하면 화면 기능을 더해도 핵심 약속이 성립하지 않는다. 인정 가능한 검증 경로가 정해진 뒤 scenarios를 완성한다.
4. **steps↔expected와 F1~F6 계약을 맞춘다.** 누락 행동, 중간 상태, 시간, 실패 조건, 문구, 설정 변경 정책을 정리한다.
5. **짧은 비교 실험으로 해법을 평가한다.** 감지 품질과 사용자 가치를 따로 본다. 사용자가 알림 뒤 실제로 행동하는지, 방해받아 끄는지, 시간 기반보다 무엇이 나아지는지 관찰한다. 목표 수치는 실험 전에 정하되 결과를 만들어 쓰지 않는다.
6. **보조 문서를 압축하고 동기화한다.** 발표 대본·세부 연구·향후 딥 모드는 부록으로, PRD에는 제품 목표·현재 범위·판정 계약·검증 계획을 둔다. 새 plan.md나 intend.md를 만드는 일은 위 결함 수정보다 후순위다.

추천 구조는 기존 YAML 키를 유지하면서 statement → 구체적 장면/대상 → 경험/손실 → 원인 가설 → 대안과 선택 이유 → insight의 근거 연결 → 최소 features → 그 계약을 검증하는 scenarios 순서로 읽히게 만드는 것이다. 키트에 없는 필드를 늘리는 것보다 기존 필드의 질문에 정확히 답하는 편이 낫다.

이번 작업에서는 원본 기획·구현·제출 내용을 바꾸지 않고 이 검토 문서만 추가했다. 로컬 자가 검사는 현재 problem.yaml의 형식적 충족 16/16을 확인했으며, 서비스 실행·E2E·대시보드 재채점은 수행하지 않았다.
